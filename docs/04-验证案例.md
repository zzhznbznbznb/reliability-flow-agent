# Reliability Flow Agent 验证案例

## 1. 验证目的

本文件定义项目关键能力的验证场景，用于检查需求理解、IR 生成、模型校验、仿真执行和结果评估是否形成可靠闭环。

验证应区分：
- **单元测试**：验证函数、Schema 和局部规则；
- **集成测试**：验证 API、IR、Runtime 和 Evaluation 之间的调用；
- **端到端测试**：验证用户输入到真实结果呈现的完整流程。

测试数据和期望值应固定并可复现。若某项业务语义尚未确认，应先将其标记为待确认，不应伪造确定的期望结果。

## 3. 详细案例

### TC-001 基础自然语言需求解析

**目的**：验证 Agent 能否从简洁需求中提取基本建模信息。

**输入示例**：

> 有 3 台同类型设备，每台设备依次执行准备、执行和结束三个活动。准备活动持续 10 分钟，执行活动持续 30 分钟，结束活动持续 5 分钟。仿真时长为 8 小时。

**预期结果**：
- 识别设备类型及数量为 3；
- 识别三个活动及其持续时间；
- 识别活动顺序；
- 识别仿真时长为 480 分钟（若系统统一使用分钟）；
- 将抽取结果形成结构化草稿；
- 不得在未确认时保存或启动仿真。

### TC-002 条件分支流程解析

**目的**：验证条件分支被保留为显式流程关系。

**输入示例**：

> 设备完成检查后，如果检查合格则进入执行活动；如果不合格则进入返工活动，返工完成后重新检查。

**预期结果**：
- 识别检查节点；
- 识别合格与不合格两个条件分支；
- 识别返工后回到检查的循环关系；
- 不得将两个分支错误地合并为固定串行流程；
- 对未定义的返工次数上限或终止条件提出澄清。

### TC-003 循环流程解析

**目的**：验证循环关系和终止条件的提取。

**输入示例**：

> 每完成一次作业后进行质量检查；若不合格则返修并重新作业，直到检查合格后结束。

**预期结果**：
- 识别作业、检查和返修活动；
- 建立不合格回路；
- 建立合格退出路径；
- 识别“直到合格”为循环终止条件；
- 若缺少最大循环次数等防护配置，应提示用户确认或采用明确的运行保护策略。

### TC-004 不完整需求澄清

**目的**：验证系统不会静默补全关键参数。

**输入示例**：

> 有若干设备执行巡检任务，设备可能发生故障，故障后需要维修。

**预期结果**：
- 识别设备数量、巡检时长、故障率、维修时长等信息缺失；
- 将缺失项标记为待确认；
- 不得擅自给出设备数量、故障率或维修时长；
- 在关键参数未满足模型要求时，不允许进入正式仿真。

### TC-005 Process IR 结构校验

**目的**：验证后端能够识别结构和引用错误。

**测试数据**：
- 构造一个合法流程模型；
- 构造一个连接指向不存在节点的模型；
- 构造一个重复节点 ID 的模型；
- 构造一个不符合 Schema 的字段类型。

**预期结果**：
- 合法模型校验通过；
- 非法引用、重复 ID 和类型错误被拒绝；
- 错误信息能够定位到相关字段或节点；
- Agent 展示的结果与后端返回内容一致。

### TC-006 Reliability IR 关联校验

**目的**：验证可靠性参数及其与 Process 模型的关联。

**测试数据**：
- 有效的可靠性参数及有效 Process 版本关联；
- 缺少必需参数的 Reliability IR；
- 参数为非法值或单位不匹配；
- Reliability IR 绑定到不匹配的 Process 版本/哈希。

**预期结果**：
- 合法数据通过校验；
- 缺失、非法或关联不匹配的数据被拒绝或产生明确错误；
- 错误信息可定位；
- 系统不自动生成虚构参数以绕过校验。

### TC-007 repair 规则验证

**目的**：在 repair 业务语义正式确认后，验证故障维修状态转换。

**前置条件**：先确认维修机制形态、维修时长、维修资源、维修期间故障暴露规则、维修完成事件及仿真结束边界。

**建议测试点**：
- 正常运行时发生故障；
- 故障后进入维修状态；
- 维修完成后恢复可运行状态；
- 维修期间是否累计故障暴露按正式规则验证；
- 维修资源不足时的等待行为（若模型包含维修资源）；
- 仿真结束时仍在维修的设备如何统计。

**预期结果**：严格匹配最终签署的业务规则和状态机定义。规则未确认前，本案例不得作为最终验收通过的依据。

### TC-008 daily 抽样验证

**目的**：在 daily 抽样规则正式确认后，验证每日故障抽样行为。

**前置条件**：明确每日抽样时刻、首日/末日边界、抽样随机机制、同一设备多日行为及维修状态交互。

**建议测试点**：
- 跨越一个日边界；
- 恰好在抽样时点开始或结束仿真；
- 设备处于维修状态时到达抽样时点；
- 固定随机种子下重复执行；
- 不同随机种子下统计行为合理。

**预期结果**：与最终规则一致，且固定配置下可复现。规则未确认前不得自行设定期望值。

### TC-009 多实体仿真

**目的**：验证多个装备实体能按模型定义独立参与仿真。

**输入配置**：
- `entity_count = 100`；
- 使用一个合法 Process IR 和 Reliability IR；
- 固定仿真时长和随机种子。

**预期结果**：
- 创建/执行 100 个装备实体；
- 统计实体数为 100；
- 不得将 100 解释为 100 次 Monte Carlo replication；
- 实体标识稳定且结果统计口径一致；
- 运行结果来自 Runtime。

### TC-010 可靠度与完好率计算

**目的**：验证指标定义和计算口径。

**测试数据示例**：
- 总设备数 \(N_{\text{total}}=10\)；
- 仿真期间曾发生故障的设备数 \(N_{\text{ever-failed}}=2\)；
- 仿真结束时处于可运行状态的设备数 \(N_{\text{operational at end}}=9\)。

**期望计算**：

\[
R=1-\frac{2}{10}=0.8
\]

\[
A=\frac{9}{10}=0.9
\]

**预期结果**：
- 设备可靠度为 0.8；
- 设备完好率为 0.9；
- 曾发生故障但仿真结束时已修复的设备，在 R 指标中仍计入曾故障设备，在 A 指标中按结束时状态统计；
- 零设备数等异常分母情形应按明确规则处理，不能产生 NaN/Infinity 并伪装为有效结果。

### TC-011 用户审批保护

**目的**：验证保存模型和启动仿真等有副作用操作必须经过用户明确确认。

**测试步骤**：
1. Agent 生成模型草稿；
2. 用户仅要求“看看模型”或“帮我检查”；
3. 观察系统是否触发正式保存或仿真；
4. 用户明确确认保存；
5. 用户明确确认启动仿真。

**预期结果**：
- 步骤 2 不触发正式保存或仿真；
- 步骤 4 仅执行被确认的模型保存；
- 步骤 5 才允许启动对应配置的仿真；
- 审批对象、模型版本和运行配置清晰可见；
- 所有执行状态以真实后端返回为准。

### TC-012 Web 端到端闭环

**目的**：验证完整的用户建模与仿真工作流。

**测试步骤**：
1. 用户在 Web 端提交自然语言需求；
2. Agent 提取实体、活动、流程关系和可靠性参数；
3. Agent 展示 Process IR 与 Reliability IR 草稿；
4. 用户补充或确认待确认项；
5. 后端执行模型校验；
6. 用户明确批准保存；
7. 用户明确批准仿真；
8. Runtime 执行；
9. Evaluation 计算指标；
10. 前端展示真实运行状态和评估结果。

**预期结果**：
- 每个阶段均有明确状态；
- 校验和仿真结果来自后端；
- 用户未批准前不执行有副作用操作；
- 运行失败时显示真实错误，不得显示伪造成功结果；
- 结果可追溯到模型版本和运行配置；
- 若结果持久化功能尚未实现，应明确标注该限制，不得声称支持历史结果查询。

## 4. 验收记录模板

每次执行验证时建议记录：

| 字段 | 内容 |
|---|---|
| 案例编号 | TC-xxx |
| 执行日期 | YYYY-MM-DD |
| 代码版本 | Git commit SHA |
| 环境 | OS、Python/Node 版本及依赖版本 |
| 输入数据 | 需求文本、IR 或运行配置 |
| 实际结果 | 后端返回及界面表现 |
| 预期结果 | 本案例规定的验收标准 |
| 结论 | Pass / Fail / Blocked |
| 证据 | 测试日志、截图、运行 ID 或结果文件 |
| 问题记录 | 差异、缺陷及后续任务 |

## 5. 验收注意事项

- 未确认的业务规则对应案例只能标记为 Blocked 或待定，不能判定通过。
- 测试通过必须有可复现的执行证据。
- Agent 的自然语言回复不能代替 API 响应、Runtime 事件或 Evaluation 数据。
- 端到端测试应覆盖正常路径和至少一种失败路径。
