## 1. 任务与设计立场

本任务从“用户如何完成一次业务流程建模和可靠性仿真实验”出发，而不是从现有技术模块、接口或页面结构出发。

设计立场如下：

1. 用户只描述业务目标和业务流程，不编写仿真代码，也不直接操作复杂建模工具。
2. Agent 负责理解自然语言、提取流程逻辑、生成模型与流程图，并在信息不足时发起澄清。
3. 系统面向通用业务流程，不将航空保障、机场、仓库或生产线作为唯一场景。
4. 流程模型与可靠性模型相互分离，通过节点标识建立关联。
5. 可靠性分析必须覆盖“潜在故障—检测发现—处理维修—恢复运行—保留历史”的完整生命周期。
6. 多台设备执行同一业务流程，但每台设备拥有独立的运行状态、故障状态和历史。
7. 分析结果同时包含理论可靠度、实际仿真统计和 Agent 的自然语言解释。
8. 需求范围覆盖从建模、配置、仿真到实验比较的完整业务闭环。

## 2. 产品定位与范围

### 2.1 系统定位

系统是一个面向通用业务流程的智能建模与可靠性仿真平台。用户通过自然语言向 Agent 描述业务目标、步骤、约束和设备信息，系统自动生成结构化流程模型与可视化流程图；用户随后编辑流程、配置设备可靠性参数、设置故障检测与维修逻辑，执行多设备仿真，并对结果进行分析和实验比较。

### 2.2 范围内能力

- 自然语言需求理解、流程逻辑提取与澄清。
- 流程模型生成、可视化、编辑、校验与保存。
- 设备可靠性节点选择、故障率 λ 配置与校验。
- 故障检测节点、故障处理路径、维修和恢复逻辑配置。
- 仿真任务创建、多设备独立运行、进度查看。
- 仿真结果统计、理论可靠度与实际统计对比、Agent 解释。
- 仿真实验保存、复现、修改、比较和参数影响分析。

### 2.3 范围外内容

- 具体自然语言处理算法、仿真算法和数据结构设计。
- 现有系统代码、Schema、API、Runtime 或前端实现。
- 页面视觉稿、交互细节、部署方案和非功能指标。
- 针对某一行业的专用模板、业务规则或设备台账。

### 4.4 用例图承载的关键业务机制

#### 4.4.1 自然语言驱动的建模闭环

用户只描述业务，系统通过“理解目标—提取步骤—识别条件/循环/约束—生成模型与流程图”形成可编辑初稿；需求存在缺失或歧义时，通过澄清扩展用例完善模型。

#### 4.4.2 流程模型与可靠性模型分离

可靠性配置不是流程图本身的一部分。流程模型描述业务节点、连接和执行时间；可靠性模型仅通过节点标识关联故障率 λ 和参与状态。未参与可靠性计算的普通业务节点不进入可靠性统计。

#### 4.4.3 潜在故障的完整生命周期

潜在故障可以先于检测发生，设备不会立即停止业务执行。只有当设备进入具备故障检测能力的节点时，潜在故障才会被发现；发现后进入故障处理和维修流程；维修完成后设备恢复正常运行，但历史故障记录永久保留。

该机制由“配置故障检测与维修—模拟设备故障生命周期—检测潜在故障—维修并恢复运行—查看故障与维修记录”共同表达。

#### 4.4.4 多设备独立运行

多台设备共享同一流程定义，但每台设备独立维护当前节点、运行状态、故障状态和运行历史。单台设备发生故障不应自动中断其他设备，因此“管理设备独立运行”是执行多设备仿真的必要子行为。

#### 4.4.5 理论可靠度与实际统计并列

“查看可靠性指标”包含“对比理论可靠度与实际统计”。理论可靠度来自可靠性参数计算，实际故障频率来自仿真事件统计；两者不能混为一谈。Agent 的解释用例用于说明差异、异常和关键结论。

#### 4.4.6 实验可追溯与可比较

实验保存模型、参数与结果；复现实验依赖相同模型和随机种子；修改参数以派生方式创建新实验；比较实验和参数影响分析支撑可靠性决策。

## 8. 假设与约束

1. 用例图只设置一个业务参与者“用户”；业务建模人员、可靠性工程师、仿真分析人员是用户在不同任务中的职责，不拆成多个外部系统。
2. 大模型、仿真引擎、存储和计算资源是系统内部能力，不作为外部参与者。
3. 可靠性配置通过节点标识与流程模型关联，不改变流程模型本身的业务含义。
4. 潜在故障可以在设备继续运行时存在，但只能在故障检测节点被发现。
5. 维修完成后设备恢复运行；历史故障、检测和维修记录不因恢复而删除。
6. 多设备共享流程定义，但运行状态、故障状态和历史彼此独立。
7. 理论可靠度与实际仿真故障统计是两类不同性质的结论，必须并列展示。
8. 本任务不包含算法设计、接口设计、数据库设计、前端实现或仿真执行。
