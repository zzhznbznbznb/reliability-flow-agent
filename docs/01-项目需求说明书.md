# Reliability Flow Agent 项目需求说明书

## 1. 项目背景

随着装备集群、设备系统及保障业务流程日益复杂，任务活动之间存在前后依赖、条件分支、循环、资源竞争和可靠性约束。传统依赖人工阅读需求、手工绘制流程图并逐项配置仿真参数的方式，建模周期较长，且需求文本、模型结构和仿真结果之间不易保持一致。

本项目拟建设自然语言驱动的流程建模与可靠性离散事件仿真智能体。用户以自然语言或需求文档描述场景，系统辅助完成需求解析、结构化建模、模型校验、仿真执行和结果分析，形成可追溯、可验证的建模实验流程。

## 2. 项目目标与范围

### 2.1 总体目标

建立一套以结构化 IR 为核心、以 Agent 为交互入口、以离散事件 Runtime 为执行基础的可靠性仿真系统，实现从业务需求到仿真评估的闭环。

### 2.2 本期目标

- 支持需求文本输入及结构化信息提取。
- 生成或辅助编辑 Process IR。
- 生成或辅助编辑 Reliability IR。
- 提供模型校验、错误定位和修正建议。
- 在用户确认后调用仿真 Runtime。
- 展示仿真过程摘要及评估指标。
- 为后续实验管理、结果持久化和多轮 Agent 任务管理预留接口。

### 2.3 不在未经确认情况下默认纳入的范围

- 自动替用户决定存在歧义的业务规则。
- 未经确认自动保存模型或启动仿真。
- 将装备实体数量解释为仿真重复试验次数。
- 在缺乏 Runtime 证据时由 Agent 直接生成仿真结果。
- 将尚未实现的会话管理、任务审批、结果持久化描述为已完成能力。

## 3. 用户与典型场景

### 3.1 用户角色

- **建模人员**：提交需求、检查模型结构、调整流程和参数。
- **仿真分析人员**：配置运行条件、执行仿真、分析指标。
- **系统管理员/开发人员**：维护模型规范、工具接口、运行环境和权限策略。

### 3.2 典型使用场景

用户提交一份装备任务保障需求，描述装备数量、任务流程、活动持续时间、设备故障率、维修规则及仿真时长。Agent 从需求中提取结构化信息，形成模型草稿，并对不明确的流程分支、维修规则或可靠性参数提出澄清问题。用户确认后，系统校验模型并运行仿真，最终展示设备可靠度、完好率、任务完成情况及相关解释。

## 4. 功能需求概述

### 4.1 需求接入与理解

系统应支持用户通过对话输入需求，并为后续 Word、PDF 等需求文件导入预留能力。Agent 应提取：
- 装备、设备及其数量；
- 任务、活动及持续时间；
- 活动之间的顺序、条件分支和循环关系；
- 资源及资源容量约束；
- 可靠性参数及适用对象；
- 故障、检测、维修和恢复规则；
- 仿真时长、实体数量及其他运行配置。

提取结果应区分原文明确给出的信息、系统推断信息和待用户确认信息。

### 4.2 流程模型构建（Process IR）

Process IR 用于描述实体执行的业务流程，包括节点、连接关系、条件、循环及必要的执行属性。系统应支持模型生成、查看、编辑、校验和版本化管理。

流程关系采用 configurable 原则：具体拓扑由模型表达，不将所有业务强制转换为固定串行流程。

### 4.3 可靠性模型构建（Reliability IR）

Reliability IR 用于描述设备或相关对象的可靠性属性，并与对应 Process 模型版本建立明确关联。可靠性参数应具备单位、适用对象和合法性约束。对于缺失或不一致的参数，系统应报告问题，而不是自行编造。

### 4.4 模型校验

校验至少包括：
- IR 结构和字段类型；
- 节点及实体标识唯一性；
- 流程连接引用有效性；
- 条件分支及循环结构合法性；
- Reliability IR 与 Process IR 的对象引用一致性；
- 可靠性参数范围和单位；
- 仿真配置的基本合法性。

校验结果必须来自后端校验接口，并返回可定位的问题信息。

### 4.5 仿真执行

系统应在用户确认模型和运行配置后调用离散事件 Runtime。Runtime 应负责事件推进、实体状态变化、故障与维修行为以及运行数据采集。Agent 不得伪造运行状态或指标。

当前已有 Python 离散事件 Runtime 基础，支持事件队列、多实体执行及可复现随机流。维修和 daily 抽样的完整语义仍需以正式规则和测试为准。

### 4.6 结果评估

Evaluation 应根据真实 Runtime 输出计算整体、节点和设备层面的指标，并支持目标判定、警告和解释信息。

当前暂定设备指标：
- 设备可靠度：\(R=1-N_{\text{ever-failed}}/N_{\text{total}}\)；
- 设备完好率：\(A=N_{\text{operational at end}}/N_{\text{total}}\)。

指标定义、统计口径和边界条件应在接口与测试中保持一致。

## 5. 关键业务规则与待确认项

| 主题 | 当前决策/状态 | 说明 |
|---|---|---|
| 流程关系 | configurable | 由用户模型定义流程拓扑 |
| 故障维修 | repair | 具体维修机制形态待确认 |
| 故障抽样 | daily | 每日抽样时点、边界和维修交互细节待确认 |
| 设备可靠度 | 已提出指标定义 | 统计仿真期间曾故障的设备占比的补数 |
| 设备完好率 | 已提出指标定义 | 统计仿真结束时处于可运行状态的设备比例 |
| 实体数量 | entity_count 表示实体数 | 不等同于 Monte Carlo replication 次数 |
| 模型保存 | 必须用户确认 | Agent 不得擅自保存 |
| 仿真启动 | 必须用户确认 | Agent 不得擅自启动 |

仍需进一步明确的事项包括：维修时长和维修资源如何建模、维修期间是否继续累计故障暴露、daily 抽样的具体时刻与时间边界、同一时刻事件的处理优先级、仿真结束时处于维修中的设备如何计入完好率等。

## 6. 非功能需求

- **可追溯性**：需求、IR 版本、仿真配置和结果应建立关联。
- **可复现性**：支持记录随机种子及运行配置。
- **可解释性**：模型字段和评估指标应能追溯到需求来源或明确的系统规则。
- **安全性**：Agent 工具应采用白名单，限制文件、命令和系统操作权限。
- **可靠性**：模型校验失败时不得进入正式仿真流程。
- **可扩展性**：IR 与 Runtime 解耦，便于增加不同领域规则和执行后端。
- **可维护性**：接口、Schema、测试和文档应保持同步。

## 7. 当前基础与主要差距

### 7.1 已有基础

- Process IR 的模型定义、校验和版本化存储基础；
- Reliability IR 的定义及与 Process 版本/哈希绑定；
- Python 离散事件 Runtime、多实体执行和可复现随机流；
- Evaluation 的整体/节点/设备指标和目标判定基础；
- React Flow 建模工作台及相关面板；
- FastAPI 相关业务 API。

### 7.2 主要差距

- 当前 AgentPanel 的交互主要由前端本地规则解析驱动，尚非完整的 LLM/Pi Agent 后端集成。
- 尚无完整的后端聊天、Session、Task 管理 API。
- 尚无完整 SSE/WebSocket 流式事件通道。
- 尚无已完成的 Pi RPC 受控子进程集成闭环。
- 仿真结果持久化、独立 result ID 和结果查询能力仍需建设。
- repair 与 daily 的完整业务语义需要进一步固化并通过测试验证。

## 8. 验收原则

每项需求应至少具备：
1. 明确的输入、输出和错误行为；
2. 对应 IR Schema 或 API 契约；
3. 自动化测试；
4. 可重复执行的验证案例；
5. 对应的实现状态和证据。

“界面上存在入口”不等同于功能验收通过；“Agent 声称成功”不等同于后端校验或仿真成功。
